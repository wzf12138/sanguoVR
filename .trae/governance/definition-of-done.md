# 集中式完成定义

任务只有在所有适用条款均满足且证据可读取时，才能进入 `awaiting_review`；只有用户或授权审批人验收后才能进入 `approved`。

## 1. 范围与边界

- 实施内容与已批准任务或变更请求一致，没有隐含扩展。
- 所有交付物位于允许路径，禁止路径和项目外位置未被修改。
- 没有临时脚本、下载、缓存、日志或调试产物污染项目。
- 未创建平行治理正文、平行知识库或第二个可发现 Skill。

## 2. 交付完整性

- 要求的文件、代码、配置或资产全部存在，非空且不是占位正文。
- 修改已有文件前已读取并保留可审计差异；删除和迁移具备明确依据。
- 相关引用、相对链接、命名、目录与依赖一致。
- 产品事实、执行约束和工程实现没有互相矛盾。

## 3. 验证证据

- 每项验收条件均对应实际执行的检查与可定位证据。
- 静态检查和适用的自动化测试已通过。
- UE 工程变更完成适用的工程生成、模块编译、编辑器加载或运行检查。
- **代码任务**：逐份回读交付文件，确认标题、正文、链接和关键约束正确。
- **资产任务**：用户在 UE Content Browser 中导航到资产路径，确认视觉效果（模型比例、材质、动画、命名）符合规格。`10-asset-register.md` 已同步。
- **关卡任务**：用户在 UE 编辑器中加载关卡，确认布局、光照、碰撞、NavMesh、性能达标。
- VR 体验变更分别标明桌面、编辑器和 PICO 真机验证层级；模拟结果不得代替真机证据。
- 未执行、无法执行或失败的检查明确记录为"待验证"或"阻塞"，不得包装成通过。

## 4. 治理同步

- 当前任务状态、实施结果、偏差、遗留风险和后续动作已记录。
- 相关索引、决策、风险、问题、资产、依赖、验证与技术债登记册已按需同步。
- `.trae/CHANGELOG.md` 已记录本次可审计变更。
- 如果改变批准基线，存在已批准的变更请求并完成关闭信息。

## 5. 文档与 Skill 验收

- 所有本次交付文档均已逐份回读，标题、正文、链接和关键约束正确。
- `.trae/skills/` 下仅存在一个带 YAML frontmatter 的 `SKILL.md`。
- 唯一可发现 Skill 路径为 `.trae/skills/three-kingdoms-vr-arena/SKILL.md`。
- 唯一 Skill 的 frontmatter 同时包含有效的 `name` 与说明功能、触发场景的 `description`。
- 已废弃 `SKILL.md` 若保留审计说明，不得含 frontmatter、`name:` 或 `description:` 元数据。

## 6. 状态判定

- "文件已创建"或"代码已编写"最多表示已实施，不自动表示已验证。
- 任一强制条款失败，任务保持 `in_progress` 或转为 `blocked`。
- 执行代理不得自行将任务标记为 `approved`。
- **禁止提前提交审核**：任务的 `TASK.md` 交付物或 `CHECKS.md` 检查项中任一未完成，执行模型不得将状态更新为 `awaiting_review`。未完成的交付物不得以"待办"、"遗留"、"后续补充"、"已规划"、"待用户执行"等任何形式包装为已交付，也不得通过将未完成项挪入报告"风险/待办"段落来绕过交付物完整性检查。

## 7. 生产就绪验收基准（Production Readiness Baseline）

> 以下基准定义每种交付物类型的"生产可用"最低门槛。CHECKS.md 检查项必须引用对应基准编号。执行模型不得以"已创建"、"已放置"、"可打开"等模糊表述替代基准验收。审核模型逐条核对基准后决定是否批准。

### 7.1 关卡（Level/Map）

| 基准 | 验收条件 | 失败信号 | 证据类型 |
|------|---------|---------|---------|
| LV-01 | 光照已构建，编辑器无 "Lighting needs to be rebuilt" 警告 | Viewport 左上角存在红色警告文字 | `[截图]` Viewport 全屏截图（含左上角） |
| LV-02 | NavMesh 覆盖全部可行走区域，覆盖率 ≥ 90% | 大面积绿色 NavMesh 缺失，或 AI 出生点不在 NavMesh 上 | `[截图]` NavMesh 可视化（P 键） |
| LV-03 | 所有放置 Actor 的 Transform 非默认值（非原点/非零旋转/非 1.0 缩放），且组件引用完整 | Actor 坐标全为 (0,0,0) 或组件引用显示黄色警告 | `[文件]` 关卡文件大小 > 1KB |
| LV-04 | 玩家出生点（PlayerStart）存在且与其他 Actor 无碰撞重叠 | PlayerStart 缺失或嵌入墙体/地面 | `[截图]` PlayerStart 位置 + 碰撞视图 |
| LV-05 | 关卡在 PIE 模式下可运行 ≥ 30 秒无崩溃 | PIE 启动即崩溃或 5 秒内卡死 | `[日志]` PIE 运行日志，含 "Play in editor" 起止行 |

### 7.2 蓝图（Blueprint）

| 基准 | 验收条件 | 失败信号 | 证据类型 |
|------|---------|---------|---------|
| BP-01 | 蓝图编译无错误、无警告 | Compiler Results 面板有红色 Error 或黄色 Warning | `[截图]` Compiler Results 面板 |
| BP-02 | 所有外部引用（SkeletalMesh、Material、Sound、其他蓝图类）可解析 | Details 面板显示黄色 "None" 或红色缺失引用 | `[文件]` .uasset 文件大小 > 5KB |
| BP-03 | 蓝图可放置在关卡中，无 "Not placeable" 或构造脚本崩溃 | 拖入 Viewport 时无响应或报错 | `[截图]` 蓝图在关卡中的实例 |
| BP-04 | 继承链正确（父类存在且非 deprecated） | Class Settings 显示父类为红色或空 | `[文件]` 蓝图父类路径引用 |

### 7.3 C++ 代码

| 基准 | 验收条件 | 失败信号 | 证据类型 |
|------|---------|---------|---------|
| CP-01 | Win64 Development Editor 编译通过，0 errors | 编译输出含 "Error:" 行 | `[日志]` 编译输出尾部摘要 |
| CP-02 | 关联自动化测试通过（如存在） | 测试输出含 "Failed" 或 "Assertion failed" | `[日志]` 测试运行输出 |
| CP-03 | 无硬编码魔法数字（路径、端口、数值常量），常量集中在 `VRTypes.h` 或对应 Data Asset | 代码中出现裸 `8000`、`"C:\\"`、`":8080"` 等 | `[文件]` 逐份回读确认 |
| CP-04 | 接口签名与 `systems/` 对应契约一致 | 函数签名参数类型、返回值、const 修饰符与契约不符 | `[文件]` 接口头文件内容 |
| CP-05 | 所有 `UE_LOG` 使用已注册的日志分类，无裸 `LogTemp` | 代码中出现 `LogTemp` 或未注册的分类名 | `[文件]` Grep 搜索 `LogTemp` |

### 7.4 资产（SkeletalMesh / StaticMesh / Texture / Material）

| 基准 | 验收条件 | 失败信号 | 证据类型 |
|------|---------|---------|---------|
| AS-01 | 资产可在 Content Browser 中预览，无 "Failed to load" 或红色叉 | 缩略图显示红色叉或空白 | `[截图]` Content Browser 缩略图 |
| AS-02 | 面数/贴图分辨率在规格预算内 | 武器 > 4K tris、贴图 > 1024 等 | `[文件]` 资产属性面板截图 |
| AS-03 | 材质槽数量 ≤ 规格上限（武器 ≤ 2，角色 ≤ 4） | 材质槽数量超标 | `[文件]` 材质槽列表截图 |
| AS-04 | 命名符合 `02-naming-and-path-standard.md` 前缀约定 | 路径或文件名不符合前缀规则 | `[文件]` 文件路径字符串 |

### 7.5 这些基准如何嵌入 CHECKS.md

决策模型生成 CHECKS.md 时，将模糊检查项替换为基准引用：

```markdown
# 模糊写法（旧，禁止）
- 关卡已创建，布局合理

# 基准写法（新，必须）
- [ ] `[截图]` LV-01 光照已构建，无 "Lighting needs to be rebuilt" 警告
- [ ] `[截图]` LV-02 NavMesh 覆盖率 ≥ 90%
- [ ] `[截图]` LV-03 所有 Actor Transform 非默认值
- [ ] `[截图]` LV-04 PlayerStart 存在且无碰撞重叠
- [ ] `[日志]` LV-05 PIE 运行 ≥ 30 秒无崩溃
```

### 7.6 代码质量的用户可验证性

> 用户无法直接判断 C++ 代码质量。以下机制替代人工代码审查：

| 机制 | 覆盖范围 | 核验方式 |
|------|---------|---------|
| 自动化测试 (CP-02) | 接口契约、状态机迁移、数据资产 Schema | 执行模型运行测试，输出 `N/N passed` |
| 接口一致性 (CP-04) | 所有接口签名 | 审核模型逐份对照 systems/ 契约 |
| 日志分类 (CP-05) | 日志输出 | Grep 搜索 `LogTemp` 返回 0 结果 |
| 编译通过 (CP-01) | 语法、链接、依赖 | 编译输出 "Result: Succeeded" |
| 无魔法数字 (CP-03) | 代码可维护性 | 审核模型抽查 |

**用户只需要确认**：编译通过 + 测试全绿 + 审核模型已对照契约检查。这三项通过了，代码质量就有保障。
