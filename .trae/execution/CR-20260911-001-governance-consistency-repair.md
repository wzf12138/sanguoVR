### 3.8 密钥检查的「范围披露」与加固时序约束（**只披露，不扩模式**）

## 10. 新增裁定：门禁项的自指分支（2026-09-12 凌晨发现）

> 本节由**备份提交动作本身触发**：提交 `4b89763` / `d9fac2a` 推送后，门禁在本机、干净浅克隆、CI 三处**同时判红**。经读判据原文 + 实测两个输入，判定为**门禁项的设计缺陷（非仓库缺陷）**，并据实记录。**本节属「判据修正」，改动 `governance/SessionCommands.md` 的判据补充与 `registers/11-tech-debt-register.md` 的 TD-018。**

### 10.1 现象（三处一致，实测非推断）

| 位置 | 结果 |
|---|---|
| 本机项目根 | 30 项 / 通过 28 / 警告 1 / **失败 1** / `EXIT=1` |
| 项目外干净浅克隆 | 同上 30/28/1/**1** / `EXIT=1` |
| CI run `#36`（`4b89763`）与 `#37`（`d9fac2a`） | 「治理校验 CI 门禁」**任务级 `failure`**、步骤级「治理一致性校验（严格模式）」**`failure`**；「看板部署」两次 `success` |
| 步骤日志端点 | **403** ⇒ **conclusion 已核验、日志正文未核验**（不得写成「已核验 CI 日志」） |

失败项：`CHANGELOG 不滞后于提交`。detail 原文：**`顶部条目 2026-09-11，HEAD 提交 2026-09-12`**。

### 10.2 根因：门禁项以 HEAD 自身日期为输入 ⇒ 自我判红

`dashboard/check-integrity.py:783-806` 的判据为 `top >= head`，其中
`head = git log -1 --format=%cs`（**HEAD 的提交日期**）、`top` = CHANGELOG 首个 `^## (\d{4}-\d{2}-\d{2})` 行的日期。

两个提交的 committer 时间为 `2026-09-12 00:00:33` / `2026-09-12 00:00:56`（**跨本地零点**），而 CHANGELOG 顶部段是 `## 2026-09-11 晚（…）`。提交前 HEAD 仍是 09-11 的 `10f0100`，故**提交前那一跑必然绿、无法预知**。

> **⇒ 「本地绿 ≠ CI 绿」在本项上有一个自指分支：绿的前提被「提交」这个动作本身破坏。**
> 这不是仓库缺陷，**也不放宽档位**；正确的应对是**把该前提纳入提交前检查**。

### 10.3 裁定

1. **判据不放宽**：`CHANGELOG 不滞后于提交` 语义成立（CHANGELOG 应覆盖 HEAD 提交日当天），**不改为 warn、不加特例**。**任何为过检而改写日期数字的行为属造假，禁止。**
2. **新增提交前检查项（写入 `governance/SessionCommands.md`）**：**跨本地零点提交前，先确认 CHANGELOG 顶部日期 ≥ 当日**；若不足，**先补写当日的如实条目**（记录当日实际发生的事），再提交。
3. **本次修复方式**：在 `.trae/CHANGELOG.md` 顶部**新增 `## 2026-09-12` 段** —— 该段内容为**据实记录**（两个提交确实发生在 09-12 凌晨，且 LFS 核验与门禁事故均发生在该日），**不是为过检而编造日期**。
4. **`dashboard/check-integrity.py` 本身本轮不改**（保持封版 `77269 B / A280C20A…`）：判据语义未变；如后续要为该项增加「跨零点窗口」提示，须另立变更并重新走「本地 + 干净克隆 + CI」三层验证。

### 10.4 同批发现：TD-018 判据收紧（LFS「输出为空」不可作判据）

提交 `4b89763`/`d9fac2a` 引入的两个 LFS 新对象（合计 **28,880,650 B**）：

| 观测 | 结果 |
|---|---|
| `git push` 输出 | **无** `Uploading LFS objects` 行 |
| `git lfs push --all origin`（连跑两次） | 均为 **0 行**输出、`exit=0` |
| `git lfs fsck` | OK |
| **第二种方法**（全新干净浅克隆 `GIT_LFS_SKIP_SMUDGE=1` 内 `git lfs fetch origin --include=<3 路径>`） | store `0 → 3 个对象 / 28,880,650 B` |
| 落地字节核对 | `730,370` / `108,682` / `28,041,598` **逐一与指针 size 精确相符** |
| 克隆内 369 个 LFS 跟踪文件 | **实体化 3 / 仍为指针 366** |

**⇒ 远端确实持有这 3 个新对象。** 而 **「`push --all` 输出为空」既可能是真阴性（无事可做）、也可能是假阴性，二者无法由该输出区分。**

**判据收紧（已写入 TD-018）**：**唯一可靠判据 = 第二种方法** —— 在干净克隆内实测 `lfs fetch` 并核对落地字节数；**不得以 `lfs push --all` 的输出为空作为「远端 LFS 完整」的判据**。
**原因未查明，不推测**（未验证假设：`git push` 的 git-lfs pre-push 钩子已先行上传，故随后 `push --all` 无事可做）。

**同批新增仪器陷阱（同族）**：`git lfs checkout` 自报 `Checking out LFS objects: 100% (369/369), 197 MB`，而**实测仅 3 个被实体化、366 个仍为指针** ⇒ **工具的聚合自报数字不可作判据，必须回读现场。**

> **本族教训累计（不追改历史，仅登记）**：① 实现者自己的 `main()` 崩溃使 in-process 测试全部绕过 `main()`；② verifier 的 `git ls-files -z` 行解析；③ 只在开发机验证门禁（`cb7ab79` 的 CI 判红）；④ 指挥台把删除函数命名为 `Del`（撞 PowerShell `Remove-Item` 内置别名）；⑤ 删除前未查编辑器进程占用；⑥ **本节的「门禁项自指」**；⑦ **本节的 `lfs checkout` 聚合自报**。
> **统一判据**：**任何「检查通过 / 未发现 / 已删除」的结论，必须来自数据源本身并**回读现场**，不得来自工具的自报数字，也不得来自「我的解析没出错」的假设。**

### 10.6 同族第二例：记录自指（本次记录过程自身暴露）

**现象**：第三提交 `a4b21d9` 完成后，指挥台把该提交写成「**本窗口终态**」并写入 `CHANGELOG.md` 与本 CR 的 §10.5；而**随即就必须再做第四个提交 `8eca4d5`** 来补齐台账（`a4b21d9` 的记录只写到「判红 + 裁定」，未写闭环，且台账缺第四行）⇒ **「终态」这句断言在写下时即已不成立。**

**与 §10.2 同型**：门禁项自指的缺陷型是「**断言的正确性依赖一个尚未发生的动作**」（判据以 HEAD 自身日期为输入，而 HEAD 由提交动作决定）；记录自指是同一缺陷型的第二个实例（「终态」以「不再有后续提交」为前提，而后续提交由记录动作本身引发）。

**判据（固化）**：

1. **记录类文本不得声称「终态 / 最终 / 本窗口结束 / 以此闭环」**；
2. **必须把断言限定到某个已知提交**，标准写法：**「截至 `<SHA>` 已核验」**；
3. **允许后续提交追加行**（台账表按提交追加，不重写历史行）；
4. **本条自身即按此写** —— 它只声称截至 `8eca4d5` 的事实，**不声称它是最后一条**。

> **族谱（两类自指）**：**门禁自指**（§10.2，判据输入含被检动作的产物）+ **记录自指**（§10.6，断言前提含被记录动作之后的动作）。**共同对策：把断言的输入/前提限定到「已经发生的、已知的」对象上，不使用「将要/最终/到此为止」这类依赖未来的措辞。**
